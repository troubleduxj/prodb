## 3. 模块设计

### 3.1 数据库管理平台

该平台是系统的控制中心，由前端和后端两部分组成。其核心功能模块分组如下：

1.  **采集器管理**:
    *   负责采集器的生命周期管理，包括注册、配置下发、状态监控和心跳检测。
    *   提供采集任务的可视化编排。
2.  **数据库管理**:
    *   负责对 TDengine 数据库本身进行管理，如数据模型（超级表）的定义和实例状态的监控。
3.  **数据库应用**:
    *   负责时序数据的查询、可视化分析以及 Dashboard 的构建与展示。
4.  **系统设置**:
    *   实现用户认证与权限管理 (RBAC)。
    *   管理系统自身的基础配置、角色和权限等元数据。

*   **后端 (Go + Gin)**:
    *   为上述所有功能模块提供 RESTful API 接口。
    *   将平台自身的业务元数据（如用户信息、采集器配置、角色权限）存储在 PostgreSQL 数据库中。

*   **前端 (React + Vite + shadcn-admin)**:
    *   为所有功能模块提供统一的图形化操作界面 (GUI)。
    *   通过调用后端 API 实现对采集器和数据库的可视化管理。

#### 3.1.1 采集器管理模块详细设计

为了实现对采集器生命周期和数据采集任务的全面管理，采集器管理模块将包含以下核心子模块和功能：

**1. 采集器实例管理 (Collector Instance Management)**

这是管理物理或虚拟采集器节点的基础。

*   **功能**:
    *   **注册与审批**: 允许管理员在平台预注册采集器，生成唯一的 `Collector-ID` 和 `Secret-Key`。可以设计一个审批流程，只有被批准的采集器才能成功认证。
    *   **列表与检索**: 提供所有采集器的列表，支持按名称、ID、状态、标签等条件进行搜索和筛选。
    *   **生命周期操作**:
        *   **启用/禁用**: 允许管理员一键启用或禁用某个采集器。被禁用的采集器将无法通过认证，也无法接收配置。
        *   **删除**: 从平台中移除采集器记录。
    *   **密钥重置**: 为已注册的采集器重新生成 `Secret-Key`，以应对密钥泄露等安全事件。
*   **核心数据模型 (PostgreSQL)**:
    *   `collectors` 表: `id`, `name`, `collector_id`, `secret_key_hash`, `status` (e.g., pending, active, disabled), `last_heartbeat_at`, `version`, `tags`, `created_at`, `updated_at`。

**2. 采集任务管理 (Collection Task Management)**

定义采集器具体“做什么”和“怎么做”。

*   **功能**:
    *   **任务创建与配置**: 允许用户创建采集任务，并配置详细参数，例如：
        *   **数据源类型**: Modbus, OPC-UA, MQTT 等。
        *   **连接参数**: IP 地址、端口、Topic、用户名/密码等。
        *   **采集点位 (Tags/Points)**: 需要读取的寄存器地址、节点 ID 等。
        *   **采集频率**: 数据读取的间隔时间（如每 5 秒）。
        *   **上报目标**: 指定数据写入 TDengine 的哪个库/表。
    *   **任务下发**: 将创建好的采集任务与一个或多个采集器实例关联。采集器通过心跳或配置拉取接口获取分配给它的任务。
    *   **任务状态监控**: 在界面上展示每个任务的执行状态（如运行中、已停止、配置错误）。
*   **核心数据模型 (PostgreSQL)**:
    *   `tasks` 表: `id`, `name`, `description`, `source_type`, `source_config` (JSONB), `schedule`, `target_config` (JSONB)。
    *   `collector_tasks` 关联表: `collector_id`, `task_id`。

**3. 配置模板管理 (Configuration Template Management)**

为了简化大量相似采集任务的配置，引入模板概念。

*   **功能**:
    *   **模板创建**: 允许用户将一组通用的采集任务配置（如针对特定型号 PLC 的 Modbus 点位表）保存为模板。
    *   **模板应用**: 在创建新任务时，可以直接从模板加载配置，只需修改少量参数（如设备 IP），即可快速完成任务创建。
*   **核心数据模型 (PostgreSQL)**:
    *   `task_templates` 表: `id`, `name`, `description`, `source_type`, `source_config` (JSONB)。

**4. 状态监控与告警 (Status Monitoring & Alerting)**

实时掌握所有采集器的运行状况。

*   **功能**:
    *   **Dashboard**: 提供一个集中展示所有采集器关键指标的仪表盘，包括在线/离线数量、健康状态分布、版本分布等。
    *   **心跳监控**: 接收并记录采集器发送的心跳包，更新其 `last_heartbeat_at` 和 `status` 字段。如果长时间未收到心跳，则将采集器标记为“离线”或“失联”。
    *   **日志查看**: (可选) 提供接口让采集器上报关键日志，方便远程诊断问题。
    *   **告警规则与通知**: 允许用户配置告警规则（如“采集器离线超过 5 分钟”），并通过邮件、短信等方式发送通知。
*   **核心数据模型 (PostgreSQL)**:
    *   `alerts` 表: `id`, `collector_id`, `rule_id`, `level`, `message`, `status` (e.g., firing, resolved), `created_at`。

#### 3.1.2 数据库管理模块详细设计

该模块负责对 TDengine 数据库的结构和状态进行管理，确保数据能够被正确、高效地存储。

**1. 数据模型设计与管理 (Data Model Design & Management)**

这是 TDengine 用得好不好的关键。平台应引导用户建立规范的数据模型。

*   **设计原则**:
    *   **超级表 (Super Table) 作为核心**: 采用“一个数据源类型一张超级表”的原则。例如，为所有 Modbus 设备创建一个名为 `modbus_metrics` 的超级表。
    *   **标签 (Tag) 用于区分设备**: 超级表使用标签来区分不同的数据源实例。例如，`modbus_metrics` 超级表可以有 `collector_id`, `device_id`, `location` 等标签。
    *   **子表 (Sub-table) 对应具体设备**: 每个独立的设备（如一个 PLC）对应一张子表，子表的名称可以用设备 ID 动态生成。数据采集器上报数据时，会自动创建子表。
*   **功能**:
    *   **超级表管理**: 提供 UI 界面，允许管理员创建、查看和修改超级表结构（定义列和标签）。平台后端将这些操作翻译成 TDengine 的 SQL DDL 语句执行。
    *   **标签管理**: 允许用户查看和管理与超级表关联的标签，方便数据筛选。
*   **后端封装**:
    *   后端需要提供一层服务来管理 TDengine 的 schema，而不是让前端直接拼接 SQL。这有助于保证安全性和一致性。

**2. 数据库实例监控 (Database Instance Monitoring)**

提供对 TDengine 集群本身的基本监控。

*   **功能**:
    *   **连接状态**: 显示管理平台后端与 TDengine 的连接状态。
    *   **节点信息**: (可选) 调用 TDengine 的 `SHOW DNODES;` 等管理命令，展示集群节点信息和状态。
*   **实现**: 后端定期执行健康检查命令，并将状态缓存起来，通过 API 暴露给前端。

#### 3.1.3 数据库应用模块详细设计

该模块的核心是让用户能方便地从海量数据中提取价值，进行可视化分析。

**1. 数据查询与可视化 (Data Query & Visualization)**

*   **功能**:
    *   **可视化查询构建器**: 提供一个图形化界面，让用户通过下拉框选择时间范围、超级表、筛选标签（如选择某个厂区的某个设备），以及要查询的指标列，而无需手写 SQL。
    *   **原始数据表格展示**: 将查询结果以表格形式分页展示，支持排序和导出为 CSV。
    *   **数据图表可视化**:
        *   将查询结果渲染成折线图、柱状图等。
        *   支持多条曲线对比（例如，对比两个不同设备的温度）。
        *   支持时间轴缩放、平移等交互操作。
    *   **SQL 编辑器 (高级功能)**: 为高级用户提供一个 SQL 编辑器，可以直接执行 TDengine SQL 查询语句，并展示结果。
*   **后端 API 设计**:
    *   `POST /api/v1/db/query`: 接收结构化的查询参数（时间范围、筛选条件、指标等），后端负责将其安全地转换为 TDengine SQL 语句并执行，返回结果。
    *   `POST /api/v1/db/raw-sql`: 接收原始 SQL 语句，执行并返回结果（需要严格的权限控制和防注入处理）。

**2. Dashboard 管理**

允许用户将常用的查询和图表组合成一个个性化的仪表盘。

*   **功能**:
    *   **创建和布局**: 允许用户创建 Dashboard，并通过拖拽的方式添加和排列不同的图表组件 (Widget)。
    *   **组件配置**: 每个图表组件都可以独立配置其数据源（即一个保存的查询）。
    *   **全局筛选**: Dashboard 支持全局时间选择器和标签筛选器，一次性应用到所有图表组件上。
    *   **保存与分享**: 用户可以保存自己的 Dashboard 布局和配置，并分享给其他有权限的用户。
*   **核心数据模型 (PostgreSQL)**:
    *   `dashboards` 表: `id`, `name`, `description`, `owner_id`。
    *   `dashboard_widgets` 表: `id`, `dashboard_id`, `widget_type` (e.g., line_chart), `query_config` (JSONB), `layout_config` (JSONB)。

**3. 工艺流程图 (Process Flow Diagram)**

该功能允许用户创建生产过程的动态、可视化的数字孪生，将实时数据绑定到图形化的设备卡片和流程图上。

*   **功能规划**:
    *   **编辑器模式**: 提供一个画布，允许用户通过拖拽的方式绘制工艺流程图。
    *   **浏览器模式**: 用于纯展示和实时监控，隐藏编辑控件。
    *   **数据绑定**: 将图上的图形元件（设备卡片）与 TDengine 中的具体数据测点（时间序列）进行关联。
    *   **实时刷新**: 在浏览器模式下，绑定的数据能实时更新，驱动图形元件的样式（如颜色、数值显示）发生变化。

*   **前端实现建议 (Frontend Design)**:
    *   **核心库选型**: 推荐使用 **React Flow** 库。它是一个功能强大且高度可定制的节点式图表库，非常适合用于构建流程图编辑器，并且与项目当前的 React 技术栈完美契合。
    *   **主要组件**:
        1.  **组件面板 (Palette)**: 界面左侧提供一个可拖拽的组件库，包含各种预设的工业图形元件（如泵、阀门、罐体、仪表盘、管道）和基础图形（矩形、圆形、文本）。
        2.  **画布 (Canvas)**: 用户可以将组件从面板拖拽到画布上，进行自由布局、连接和缩放。
        3.  **属性检查器 (Inspector)**: 选中画布上的任一元件，界面右侧会弹出其属性配置面板。用户在此处可以：
            *   设置静态属性：如元件的标签、颜色、尺寸。
            *   **配置数据绑定**: 这是核心。提供一个交互界面，让用户能方便地选择一个 TDengine 中的数据测点（例如，通过选择超级表 -> 筛选标签 -> 选择子表 -> 选择列），并将其与元件的某个动态属性（如显示的数值、罐体的填充高度、管道的流动状态）进行绑定。

*   **后端实现建议 (Backend Design)**:
    *   **API 接口**:
        *   **`CRUD /api/v1/diagrams`**: 提供标准的增删改查接口，用于保存和加载流程图的布局和配置。流程图的完整状态（包括所有元件的位置、属性和数据绑定信息）可以序列化为一个 JSON 对象后存储。
        *   **`GET /api/v1/data-points`**: 提供一个用于数据点搜索的辅助接口，方便前端在配置数据绑定时，能动态搜索和选择 TDengine 中可用的数据测点。
    *   **实时数据推送 (Real-time Data)**:
        *   **技术选型**: 强烈建议使用 **WebSocket**。相比于前端轮询，WebSocket 可以由后端主动推送数据，延迟更低，效率更高。
        *   **工作流程**:
            1.  当用户打开一个流程图的浏览器时，前端通过 WebSocket 连接到后端。
            2.  前端发送一个 `subscribe` 消息，其中包含当前图上所有已绑定的数据测点列表。
            3.  后端收到后，为该连接维护一个数据点订阅列表，并启动一个任务，定期（如每秒）从 TDengine 中批量查询这些测点的最新值。
            4.  当查询到新数据时，后端立即通过 WebSocket 将数据推送给前端。
            5.  前端收到数据后，更新对应的图形元件状态。

*   **核心数据模型 (PostgreSQL)**:
    *   `diagrams` 表: `id`, `name`, `description`, `content` (JSONB, 用于存储 React Flow 的完整状态), `owner_id`, `created_at`, `updated_at`。

#### 3.1.4 系统管理模块详细设计

该模块负责平台自身的安全、配置和可维护性，是整个系统稳定运行的基石。它将整合并扩展原有的权限认证体系设计。

**1. 用户管理 (User Management)**

*   **功能**:
    *   **用户列表与检索**: 提供平台所有用户的列表，支持按用户名、角色、状态等进行搜索。
    *   **用户创建与编辑**: 管理员可以创建新用户，设置初始密码，并为用户分配一个或多个角色。
    *   **状态管理**: 管理员可以启用或禁用用户账户。被禁用的用户将无法登录。
    *   **个人中心**: 普通用户可以修改自己的密码和个人信息。
*   **核心数据模型 (PostgreSQL)**:
    *   `users` 表: `id`, `username`, `password_hash`, `email`, `status` (e.g., active, disabled), `created_at`, `updated_at`。

**2. 基于角色的访问控制 (Role-Based Access Control, RBAC)**

这是系统权限管理的核心，实现用户、角色、权限三者分离。

*   **功能**:
    *   **角色管理**:
        *   创建、编辑和删除角色（如“系统管理员”、“运维工程师”、“只读观察员”）。
        *   为每个角色批量授予或撤销权限。
    *   **权限管理**:
        *   系统预定义好所有可分配的权限点，并以 `资源:操作` 的格式进行管理（如 `collector:create`, `dashboard:edit`）。
        *   权限点应与后端的 API 路由和前端的菜单/按钮进行精确对应。
    *   **用户-角色分配**: 在用户管理界面，将一个或多个角色分配给指定用户。
*   **核心数据模型 (PostgreSQL)**:
    *   `roles` 表: `id`, `name`, `description`。
    *   `permissions` 表: `id`, `resource`, `action`, `description`。
    *   `user_roles` 关联表: `user_id`, `role_id`。
    *   `role_permissions` 关联表: `role_id`, `permission_id`。
*   **实现流程**:
    1.  **登录**: 用户登录成功后，后端生成 JWT，其 Payload 中包含 `user_id` 和 `roles` 列表。
    2.  **前端鉴权**: 前端根据用户角色和一份完整的权限列表（通过 `/api/v1/users/me/permissions` 获取），动态生成可访问的菜单和可操作的按钮。
    3.  **后端鉴权**: 后端 API 通过一个中间件，解析请求中的 JWT，获取用户角色，并校验该角色是否有权限访问当前 API 对应的资源和操作。

**3. 操作日志 (Audit Log)**

记录关键操作，用于安全审计和问题追溯。

*   **功能**:
    *   **日志记录**: 自动记录所有用户的关键操作，例如：用户登录、创建采集器、修改角色权限、删除数据等。
    *   **日志查询**: 提供日志查询界面，支持按操作人、时间范围、操作类型等条件进行筛选和查看。
*   **核心数据模型 (PostgreSQL)**:
    *   `audit_logs` 表: `id`, `user_id`, `action`, `resource_type`, `resource_id`, `details` (JSONB), `ip_address`, `created_at`。

**4. 系统配置 (System Configuration)**

为平台提供一个集中管理全局参数的地方。

*   **功能**:
    *   提供一个 UI 界面，用于管理那些不常变动但需要可配置的系统级参数，例如：
        *   邮件服务器 (SMTP) 配置（用于发送告警通知）。
        *   第三方服务集成的 API Key。
        *   系统默认语言、时区等。
*   **核心数据模型 (PostgreSQL)**:
    *   `system_configs` 表: `key` (PRIMARY KEY), `value` (TEXT), `description`。

### 3.2 日志管理系统

为了实现对采集器和平台后端服务的全面监控、故障排查和性能分析，系统将引入一个集中式的日志管理系统。

- **技术选型**: 推荐采用 **Grafana Loki** 技术栈，它具有轻量级、高性价比、与监控生态（Prometheus, Grafana）无缝集成的显著优势。
- **核心流程**:
    1.  **日志生成**: 所有服务（采集器、后端API）将日志以结构化的 **JSON 格式**输出到标准输出 (`stdout`)。
    2.  **日志收集**: 在服务运行环境中部署 **Promtail** 代理，负责收集日志，并为日志流附加关键元数据标签（如 `service`, `instance`, `level`）。
    3.  **日志聚合与存储**: Promtail 将日志流推送到 **Loki** 服务进行集中存储和索引。
    4.  **查询与可视化**: 用户通过 **Grafana** 平台，使用 **LogQL** 查询语言对日志进行实时检索、分析和可视化。

详细的架构设计、日志规范和实施建议，请参考独立的 **[日志管理系统设计方案](./02_model_design/log_management_design.md)**。

### 3.3 数据采集器

采集器是一个可独立部署在边缘设备或服务器上的应用程序，负责数据的采集和上报。与数据库管理平台不同，采集器是一个纯粹的后端（无头）服务，不包含任何前端用户界面，其所有配置和监控均通过管理平台远程进行。

*   **核心功能**:
    *   **独立运行**: 使用 Go 语言开发，可交叉编译为无依赖的单一二进制文件，适应多种操作系统和硬件架构 (x86, ARM)。
    *   **多协议采集**: 根据从管理平台下发的配置，通过 MQTT, OPC-UA, Modbus 等协议连接数据源并采集数据。
    *   **数据上报**: 将采集到的数据高效写入中心 TDengine 数据库。
    *   **状态监控**: 定期向管理平台发送心跳，上报自身运行状态。

*   **存储转发机制 (Store-and-Forward)**:
    *   **目的**: 确保在网络不稳定的环境下数据的完整性和可靠性。
    *   **实现**:
        1.  **本地缓存**: 内置轻量级数据库 **SQLite** 作为本地数据缓存。
        2.  **工作流程**: 当与中心 TDengine 的网络连接中断时，采集器会将数据临时存入本地 SQLite。
        3.  **自动重传**: 采集器后台任务会定期检测网络连接。一旦连接恢复，它将自动从 SQLite 读取缓存数据，并按时序顺序重新上报至 TDengine。
        4.  **数据确认**: 只有当数据被 TDengine 成功接收后，才会从本地缓存中删除，防止数据丢失。

## 4. 通信协议设计

为了确保管理平台与采集器之间通信的安全性、可靠性和效率，特设计以下通信方案。

### 4.1 服务发现

采集器通过预配置的方式发现管理平台。

*   **配置方式**: 管理平台的访问地址将通过**域名**（而非固定 IP）的形式，在采集器部署时通过环境变量或本地配置文件（`collector.conf`）进行配置。
*   **优点**:
    *   **简单可靠**: 实现简单，满足当前阶段需求。
    *   **灵活性**: 使用域名便于后台服务的迁移和扩展，只需更新 DNS 解析即可，无需修改采集器配置。

### 4.2 通信协议与 API 设计

*   **协议**: **HTTPS (HTTP over TLS)**
    *   **原因**:
        *   **安全性**: 通过 TLS 加密传输通道，防止数据在网络传输过程中被窃听或篡改。
        *   **标准化与通用性**: 基于标准的 RESTful API 设计，易于实现、调试和跨平台。
        *   **无状态**: 简化服务器端设计，便于未来进行水平扩展。

*   **API 设计原则**:
    *   **API 版本控制**: 所有 API 路径都将包含版本号，例如 `/api/v1/`，以确保未来的向后兼容性。
    *   **健壮的错误处理**: 采集器在调用 API 时，将实现**指数退避重试**机制，以应对临时的网络中断或服务端错误，提高通信的可靠性。

### 4.3 认证与授权机制

采用基于 `ID/Secret` 和有时效性 `Access Token` + `Refresh Token` 的双重认证机制，确保只有合法的采集器才能接入平台，并兼顾安全与便利。

1.  **采集器身份注册与密钥管理**:
    *   每个采集器在部署前，必须在管理平台进行注册，平台将为其生成唯一的 **`Collector-ID`** 和高强度密钥 **`Secret-Key`**。
    *   `Collector-ID` 用于标识身份，`Secret-Key` 用于首次认证。
    *   **安全要求**: `Secret-Key` 必须在采集器端**加密存储**，并严格控制其文件权限，严禁在代码或配置文件中明文存储。

2.  **动态 Token 获取与刷新**:
    *   **首次认证**: 采集器启动后，使用其 `Collector-ID` 和 `Secret-Key` 调用认证接口 (`/api/v1/auth/login`)，获取一组有时效性的 **Access Token** 和 **Refresh Token**。
        *   **Access Token**: 短周期（如 1 小时），用于日常 API 请求的认证。
        *   **Refresh Token**: 长周期（如 7 天），专门用于刷新即将过期的 Access Token。
    *   **Token 刷新**: Access Token 即将过期时，采集器应使用 Refresh Token 调用刷新接口 (`/api/v1/auth/refresh`)，获取新的 Access Token，而无需再次使用 `Secret-Key`。这大大降低了 `Secret-Key` 的暴露风险。

3.  **API 请求认证**:
    *   在 Access Token 有效期内，采集器发起的每个 API 请求都必须在 HTTP Header 中携带此 Token (`Authorization: Bearer <access_token>`)。
    *   平台后端在处理任何请求前，都会严格校验 Access Token 的有效性（包括签名和有效期）。
    *   如果 Access Token 过期，采集器需要先执行 Token 刷新流程。如果 Refresh Token 也过期，则需要使用 `Secret-Key` 重新进行首次认证。

4.  **授权粒度**:
    *   JWT Token 的 Payload 中将包含 `collector_id`，确保采集器只能访问其自身相关的资源，实现精细化的权限控制。

### 4.4 核心 API 接口

*   **`POST /api/v1/auth/login` (首次认证)**
    *   **说明**: 采集器使用 `Collector-ID` 和 `Secret-Key` 进行身份认证，获取用于后续所有通信的 `Access Token` 和 `Refresh Token`。

*   **`POST /api/v1/auth/refresh` (刷新 Token)**
    *   **说明**: 采集器使用有效的 `Refresh Token` 获取新的 `Access Token`。

*   **`GET /api/v1/config` (获取配置)**
    *   **说明**: 采集器启动或定期轮询时调用此接口，从平台获取最新的采集任务指令（如采集点、协议、频率等）。

*   **`POST /api/v1/heartbeat` (发送心跳)**
    *   **说明**: 采集器定期（如每分钟）调用此接口，向平台报告其存活状态和关键性能指标。平台可据此实现对采集器的在线状态监控和告警。

*   **`POST /api/v1/alerts` (上报告警)**
    *   **说明**: 当采集器在运行中遇到严重错误（如无法连接数据源）时，通过此接口主动向管理平台上报告警信息。
